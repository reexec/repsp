# 설계: 오디오 끊김 — GE 리스트 실행 중 굶는 사운드 스레드, 호스트 쪽 버퍼링 (issue #28)

## 1. 요구사항

* 소비자([reDMP1 issue #28](https://github.com/reexec/reDMP1/issues/28))에서 사용자가 귀와 녹화로 확인했다: 소프트웨어 렌더러에서는 소리가 전체적으로 끊기고 음악이 느리게 들린다. OpenGL 렌더러에서는 대부분 사라지지만 완전히는 아니다. 녹화의 소리는 약 20 ms 소리와 10 ms 무음이 반복되는 모양이었다.
* 소리의 연속성이 렌더러의 속도에 좌우되지 않아야 한다.
* 원인을 측정으로 확정한 뒤 고친다.

## 2. 가설

* **H1 — GE 리스트 실행 중 선점 불가**: GE 리스트는 호출한 게스트 스레드 위에서 끝까지 실행된다. 게스트 스레드의 전환은 스케줄러 진입 지점(HLE 호출)에서만 일어난다(`YieldIfPreempted`). 오디오 클록이 우선순위가 높은 사운드 스레드를 깨워도, 실행 중인 스레드가 리스트 실행을 마치고 다음 스케줄러 지점에 올 때까지 돌지 못한다. 소프트웨어 래스터라이저에서는 한 리스트가 수십 ms 걸린다.
* **H2 — 호스트 장치가 끌어가는 단위와 게스트 큐 깊이의 불일치**: `repsp_hle_audio`의 채널은 "재생 중인 블록 하나 + 대기 블록 하나"만 받는다(256 샘플 채널이면 최대 약 11.6 ms 분량). 호스트 오디오 장치가 한 번에 그보다 많이(예: 1024 프레임, 23 ms) 끌어가면, 스케줄링이 완벽해도 매번 모자란다. 이것이 OpenGL에서도 남는 끊김의 원인일 수 있다.
* **H3 — 긴 게스트 계산**: HLE 호출 없이 오래 도는 게스트 코드(디코딩, 로딩)도 같은 방식으로 선점을 막는다. 이번에는 측정만 한다.

## 3. 측정 수단(먼저 만든다)

* 스케줄러: 스레드가 깨워진 시각부터 실제로 실행을 시작한 시각까지의 지연(wake latency)을 대기 종류별·우선순위별 히스토그램으로 센다(진단 옵션, 꺼져 있을 때 비용 없음).
* `repsp_hle_audio`: 호스트가 끌어갈 때마다 요청 프레임 수, 그때의 채널별 큐 깊이, 모자란 프레임 수를 센다. 모자라면 **실제 underrun**으로 센다(지금 통계가 0으로 남는 결함 수정). 끌어가는 단위의 분포를 통계에 낸다.
* GE: 리스트 하나의 실행 시간 분포(백엔드별).
* 이 통계로 H1·H2·H3 각각이 끊김에 얼마나 기여하는지 수치로 가른다.

## 4. 수정

* **H1 — GE 실행 중 선점 지점**: `repsp_gpu`의 인터프리터가 일정 단위(명령 수 또는 primitive 수, 그리고 경과 시간)마다 "양보 지점" 콜백을 부른다. `repsp_hle_ge`가 그 콜백을 스케줄러의 선점 확인에 연결한다. `repsp_gpu`는 스케줄러를 모른다(콜백만 받는다).
  * 양보는 "우선순위가 더 높은 준비 스레드가 있을 때만"이다(기존 `YieldIfPreempted`의 규칙 그대로). 같은 우선순위로는 넘기지 않는다. 스케줄러의 의미는 바뀌지 않고 선점 지점이 늘어날 뿐이다.
  * 양보한 동안 다른 스레드가 GE HLE를 부를 수 있다. 리스트 큐와 인터프리터 상태가 그 재진입에서 깨지지 않아야 한다: 실행 중인 리스트가 있을 때 들어온 `ListEnQueue`는 큐에 넣기만 하고, `UpdateStallAddr`·`ListSync`·`DrawSync`·`Break`·`Continue`·콜백 설정의 동작을 경우별로 정한다(실행 중인 리스트의 소유 스레드가 계속 실행한다). 인터럽트 문맥(GE 콜백)에서는 양보하지 않는다.
  * OpenGL 백엔드에서는 명령 기록이 빠르므로 양보 지점의 비용이 드러나지 않아야 한다(시간 확인은 드물게).
* **H2 — 호스트 쪽 버퍼**: 측정에서 불일치가 확인되면, 호스트 장치와 게스트 채널 사이에 작은 중간 버퍼를 둔다. 오디오 클록이 게스트 채널에서 **작은 단위(채널의 블록 크기 이하)** 로 일정하게 끌어와 중간 버퍼에 쌓고, 장치는 중간 버퍼에서 끌어간다. 게스트의 출력 대기는 지금처럼 "게스트 큐가 소비되는 속도"에 맞춰진다(게스트가 보는 의미는 그대로).
  * 중간 버퍼의 목표 깊이(지연)는 설정값이다(기본값은 측정으로 정하되 장치가 끌어가는 단위의 1~2배; 소비자가 바꿀 수 있다). 지연은 리듬 게임에서 중요하므로 통계에 실제 깊이를 낸다.
  * headless의 dummy 장치도 같은 경로를 쓴다(결과가 같아야 한다).
* **H3**: 고치지 않는다. 측정 결과를 작업 로그에 적고, 필요하면 질문으로 올린다(게스트 코드 안의 선점은 생성 코드의 계약에 닿는 설계 판단이다).

## 5. 이번 task의 검증

1. `ge_probe` 또는 새 probe: 긴 리스트를 실행하는 스레드와, 주기적으로 깨는 더 높은 우선순위의 스레드를 두고, 높은 우선순위 스레드의 wake latency가 양보 단위 안에 드는 것을 확인한다. 양보 중 다른 스레드의 `ListEnQueue`가 순서를 깨지 않는 것을 확인한다.
2. `audio_probe`: 장치가 게스트 큐보다 큰 단위로 끌어가도 생산이 제때면 underrun이 0이고, 생산이 늦으면 underrun이 세어진다. 중간 버퍼의 깊이가 설정대로다.
3. 기존 probe가 그대로 통과한다(GE 리스트의 실행 순서, 콜백 순서가 바뀌지 않는다).
4. Win64 Debug/Release, Linux x64 Debug/Release 빌드와 CTest.

# Design: audio gaps — sound threads starved while a GE list runs, host-side buffering (issue #28)

## 1. Requirements

Confirmed by ear and from a recording in the consumer ([reDMP1 issue #28](https://github.com/reexec/reDMP1/issues/28)): with the software renderer all sound has gaps and music seems slow; with the OpenGL renderer most of that is gone, but not all. The recording's audio repeated about 20 ms of sound and 10 ms of silence. Continuity of sound must not depend on the renderer's speed. Causes are confirmed by measurement before fixing.

## 2. Hypotheses

**H1 — no preemption while a GE list runs**: a list runs to completion on the calling guest thread, and guest threads switch only at scheduler entry points (HLE calls, `YieldIfPreempted`); a higher-priority sound thread woken by the audio clock cannot run until the running thread finishes the list and reaches the next scheduler point, and with the software rasterizer one list takes tens of milliseconds. **H2 — the host device's pull size versus the guest queue depth**: a `repsp_hle_audio` channel accepts only "one playing block plus one queued block" (about 11.6 ms at most for a 256-sample channel); if the host audio device pulls more than that at once (1024 frames, 23 ms, say) it comes up short every time even with perfect scheduling — possibly the cause of the gaps that remain with OpenGL. **H3 — long guest computation**: guest code that runs long without an HLE call (decoding, loading) blocks preemption the same way; measured only, this time.

## 3. Measurement (built first)

Scheduler: the delay from a thread being woken to it actually starting to run (wake latency), as histograms per wait type and priority (a diagnostic option, free when off). `repsp_hle_audio`: at every host pull, the frames requested, each channel's queue depth at that moment and the frames short; a shortfall counts as a **real underrun** (fixing the statistic that stays at zero), and the distribution of pull sizes goes into the statistics. GE: the distribution of the run time of one list, per backend. These figures separate how much each of H1, H2 and H3 contributes.

## 4. Fixes

**H1 — preemption points during GE execution**: the interpreter in `repsp_gpu` calls a "yield point" callback every so many commands or primitives and after a given elapsed time; `repsp_hle_ge` connects it to the scheduler's preemption check. `repsp_gpu` knows nothing of the scheduler (it only takes a callback). Yielding happens only when a higher-priority thread is ready (the existing rule of `YieldIfPreempted`), never to equal priority; scheduler semantics do not change, there are just more preemption points. While yielded another thread may call the GE HLE, and the list queue and interpreter state must survive that re-entry: a `ListEnQueue` arriving while a list is running only queues, and the behaviour of `UpdateStallAddr`, `ListSync`, `DrawSync`, `Break`, `Continue` and callback registration is defined case by case (the thread that owns the running list keeps executing it). No yielding in interrupt context (GE callbacks). With the OpenGL backend, where recording commands is fast, the cost of yield points must not show (the time check is infrequent).

**H2 — a host-side buffer**: if the measurement confirms the mismatch, a small intermediate buffer sits between the host device and the guest channels. The audio clock pulls from the guest channels steadily in **small units (no larger than a channel's block)** into the intermediate buffer, and the device pulls from that. The guest's blocking output is paced, as now, by how fast the guest queue is consumed (what the guest sees is unchanged). The intermediate buffer's target depth (latency) is a setting (the default is chosen from the measurements, one to two device pull sizes; the consumer can change it); since latency matters to a rhythm game the actual depth is reported in the statistics. The headless dummy device uses the same path (results must agree).

**H3**: not fixed. The measurements go into the work log and, if needed, a question is raised (preemption inside guest code touches the generated code contract, a design decision).

## 5. Verification for this task

1. `ge_probe` or a new probe: with one thread running a long list and a higher-priority thread waking periodically, the latter's wake latency stays within the yield unit; a `ListEnQueue` from another thread during a yield does not break the order.
2. `audio_probe`: when the device pulls in units larger than the guest queue, underruns are zero if production is on time and counted if it is late; the intermediate buffer depth follows the setting.
3. Existing probes pass unchanged (the order of list execution and callbacks is unchanged).
4. Win64 Debug/Release and Linux x64 Debug/Release builds and CTest.
