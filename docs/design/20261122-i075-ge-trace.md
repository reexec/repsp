# 설계: GE 그리기·텍스처 추적과 그것이 찾은 텍스처 결함 수정 (issue #75)

소비자 요구: [reexec/reDMP2#15](https://github.com/reexec/reDMP2/issues/15).

## 1. 현상 (확인됨)

* 소비자의 곡 선택 화면에서 실행 중에 만들어지는 글자(곡 목록)가 깨진다. 글자 모양은 알아볼 수 있지만 획 안팎에 픽셀 단위 잡음이 있다.
* headless 소프트웨어 렌더링(프레임 덤프)과 창 모드 GL 렌더링에서 똑같이 깨진다. 따라서 GL 텍스처 캐시처럼 한쪽에만 있는 경로는 원인이 아니다. 원인은 둘이 함께 쓰는 곳(`texture_decode.cpp`, GE 상태 해석)이거나, 게스트가 쓴 텍스처 데이터 자체다.
* 같은 화면의 고정 이미지 글자(버튼 안내, 메뉴 제목)는 정상이다.
* 소비자는 글꼴 라이브러리를 import하지 않는다. 글자는 게스트 코드가 직접 만든다.

## 2. 추적 (선택 사항, 기본 꺼짐)

* 환경 변수 두 개로 켠다:
  * `REPSP_GE_TRACE=<디렉터리>`
  * `REPSP_GE_TRACE_FRAMES=<시작>-<끝>`: 표시 프레임 번호, `REPSP_FRAME_DUMP`의 번호와 같다.

  꺼져 있으면 비용이 없어야 한다. 플래그 하나만 검사한다.
* 구간 안의 그리기(PRIM, BEZIER/SPLINE 포함)마다 `ge_trace.txt`에 한 줄을 쓴다:
  * 프레임, 리스트 번호, 그리기 순번, 프림 종류, 정점 수
  * 정점 형식(through 여부, UV 형식, 색 형식), UV 범위, 화면 좌표 범위
  * 텍스처: 켜짐, 주소, 형식, `w`/`h`/`bw`, swizzle, 레벨 수, 필터, wrap, `tex_func`, UV scale/offset
  * CLUT: 형식, shift, mask, start, 로드한 항목 수
  * 블렌드와 알파 테스트 상태
  * 텍스처 내용 해시
* 고유 텍스처(주소, 형식, 크기, 내용 해시, CLUT 해시)마다 한 번 파일을 쓴다:
  * 원시 바이트(`.bin`, 텍스처와 CLUT)
  * `DecodeTextureRgba8`로 디코드한 이미지(`.bmp`, 알파는 검은 바탕 위에 합성)
* 타이틀 중립 진단이다. 출력 파일은 게임 데이터이므로 커밋하지 않는다.

## 3. 원인 가르기

추적으로 곡 목록 영역에 그려지는 그리기를 찾고, 그 텍스처를 본다.

| 관찰 | 뜻 | 할 일 |
|---|---|---|
| 디코드 이미지는 깨끗한데 화면이 깨짐 | 샘플링·UV·scale·필터·블렌드 쪽 | repsp에서 수정 |
| 디코드 이미지가 깨짐. 원시 바이트를 다른 해석(형식, swizzle, nibble 순서, CLUT shift/mask/start)으로 보면 깨끗함 | 디코드나 상태 해석 결함 | repsp에서 수정 |
| 어떤 해석으로도 깨짐 | 게스트가 쓴 데이터 자체가 틀림 | 그 텍스처 주소에 쓰는 코드를 찾아(HLE 복사 `sceDmac`·`memcpy` 계열인지, 게스트 코드인지) 근거와 함께 보고하고 멈춘다. lift 결함이면 소비자의 일이다. |

수정의 근거는 공개 문서·PSPSDK·기존 repsp 구현만 쓴다. PPSSPP 코드는 보지 않는다.

## 4. 검증

1. 추적의 probe 또는 단위 검사: 꺼진 상태에서 출력이 없다. 구간 밖에서도 출력이 없다. 한 그리기에 한 줄이 쓰인다.
2. 수정이 repsp에 있으면 그 결함을 재현하는 probe(`texture_decode` 또는 GE 상태 검사)를 둔다.
3. 소비자 곡 선택 화면에서 곡 목록 글자가 깨끗하다. headless 프레임 덤프와 창 모드 둘 다 확인한다. 다른 화면(타이틀, 모드 선택, 곡 플레이, 결과)이 나빠지지 않는다.
4. CTest 전부 통과. Win64 Debug/Release 경고 0. Linux는 CI.

# Design: GE draw and texture trace, and the texture defect it finds (issue #75)

Consumer need: [reexec/reDMP2#15](https://github.com/reexec/reDMP2/issues/15).

## 1. Symptom (confirmed)

* Text made at runtime on the consumer's song select screen (the song list) is garbled. The glyphs are recognizable, but there is pixel-level noise inside and around the strokes.
* It is garbled identically in headless software rendering (frame dumps) and windowed GL rendering. Paths that only one side has, such as the GL texture cache, are therefore not the cause. The cause is either code both share (`texture_decode.cpp`, GE state interpretation) or the guest-written texture data itself.
* Fixed-image text on the same screen (button hints, menu titles) is fine.
* The consumer imports no font library; its own code makes the glyphs.

## 2. Trace (optional, off by default)

* Two environment variables turn it on:
  * `REPSP_GE_TRACE=<directory>`
  * `REPSP_GE_TRACE_FRAMES=<first>-<last>`: presented frame numbers, the same numbering as `REPSP_FRAME_DUMP`.

  Off, it must cost nothing beyond one flag check.
* Each draw in the range (PRIM, including BEZIER/SPLINE) writes one line to `ge_trace.txt`:
  * frame, list number, draw index, primitive type, vertex count
  * vertex format (through mode, UV format, colour format), UV range, screen-coordinate range
  * texture: enabled, address, format, `w`/`h`/`bw`, swizzle, level count, filters, wrap, `tex_func`, UV scale/offset
  * CLUT: format, shift, mask, start, loaded entry count
  * blend and alpha-test state
  * the texture content hash
* Each unique texture (address, format, size, content hash, CLUT hash) is written once:
  * raw bytes (`.bin`, texture and CLUT)
  * an image decoded with `DecodeTextureRgba8` (`.bmp`, alpha composited over black)
* This is a title-neutral diagnostic. Its output is game data and is never committed.

## 3. Telling the causes apart

Use the trace to find the draws that land in the song list area, then look at their textures.

| Observation | Meaning | Action |
|---|---|---|
| The decoded image is clean, but the screen is garbled | Sampling, UV, scale, filtering or blending | Fix in repsp |
| The decoded image is garbled, but the raw bytes look clean under another reading (format, swizzle, nibble order, CLUT shift/mask/start) | A decode or state-interpretation defect | Fix in repsp |
| Garbled under every reading | The guest-written data itself is wrong | Find the code that writes that texture address (an HLE copy such as `sceDmac` or the `memcpy` family, or guest code), report it with evidence, and stop. A lift defect is the consumer's job. |

Fixes rest only on public documents, PSPSDK and existing repsp code. PPSSPP code is not read.

## 4. Verification

1. A probe or unit check for the trace: nothing is written when it is off, nothing outside the frame range, and one line per draw.
2. If the fix is in repsp, a probe reproduces the defect (a `texture_decode` or GE-state check).
3. On the consumer's song select screen the song list text is clean, checked in both headless frame dumps and windowed mode. Other screens (title, mode select, song play, result) do not regress.
4. All CTest pass; Win64 Debug/Release with zero warnings; Linux in CI.
