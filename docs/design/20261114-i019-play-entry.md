# 설계: 플레이 진입 도중의 수정 (issue #19)

## 1. 요구사항

* 소비자([reDMP1 issue #20](https://github.com/reexec/reDMP1/issues/20))가 메뉴에서 플레이 화면까지 들어가는 동안 만나는 repsp의 결함을 고친다. 무엇이 나올지는 실행해야 알 수 있으므로, 이 설계는 범위와 원칙을 정한다.

## 2. 범위

* **GE**: 해석하지 않는 명령, 그리지 않는 primitive 종류, 지원하지 않는 텍스처 형식(인덱스 형식과 CLUT, 압축 형식 포함)·필터·래핑, 블렌드 모드, 알파·색·깊이·스텐실 테스트, 시저, 텍스처 함수(modulate, decal, blend, replace, add), 정점 형식의 조합.
* **HLE**: 이미 등록한 라이브러리 안의 미구현 함수·모드, 반환값과 부작용의 차이.
* **오디오**: SAS와 sceAudio 경로의 결함. ATRAC3plus·H.264의 실제 디코딩은 범위가 아니다.
* 스케줄러의 의미(선점 시점, 깨우는 순서, 콜백 시점)와 소비자 계약은 바꾸지 않는다. 바꿔야 한다면 근거를 소비자 작업 로그의 질문으로 올린다.

## 3. 수정 원칙

* 실제 동작을 공개 자료(PSPSDK 헤더, psdevwiki, uOFW)로 확인한 뒤 고치고, KB의 해당 항목을 **확인됨** 또는 **추정**으로 갱신한다. 확인하지 못한 것은 추정으로 적는다.
* GE의 동작에서 벗어난 임시 보정(특정 색 버리기, 좌표 밀기)은 넣지 않는다.
* 모든 수정에는 그 결함을 다시 잡는 probe를 더한다(합성 데이터).
* 지원하지 않는 것을 만났을 때 조용히 넘어가지 않도록, 통계나 한 번만 찍는 경고로 드러나게 한다(예: 처음 본 미지원 텍스처 형식, 미지원 블렌드 식).
* 타이틀의 이름이나 주소를 코드·probe·문서에 쓰지 않는다.

## 4. 이번 task의 검증

1. 더한 수정마다 probe가 있고 통과한다.
2. Win64 Debug/Release, Linux x64 Debug/Release 빌드와 CTest. probe는 실제 게임 데이터를 쓰지 않는다.

# Design: fixes on the way into gameplay (issue #19)

## 1. Requirements

Fix the repsp defects the consumer ([reDMP1 issue #20](https://github.com/reexec/reDMP1/issues/20)) meets between its menus and a gameplay screen. What turns up is only known by running, so this design sets the scope and the rules.

## 2. Scope

**GE**: undecoded commands, primitive kinds not drawn, unsupported texture formats (including indexed formats with a CLUT and compressed formats), filters and wrap modes, blend modes, the alpha, colour, depth and stencil tests, scissor, texture functions (modulate, decal, blend, replace, add), and vertex format combinations. **HLE**: unimplemented functions and modes inside libraries already registered, and differences in return values and side effects. **Audio**: defects in the SAS and sceAudio paths; real ATRAC3plus and H.264 decoding is out of scope. Scheduler semantics (when preemption happens, wake order, callback timing) and consumer contracts are not changed; if a change is needed, the evidence is raised as a question in the consumer's work log.

## 3. Rules for fixes

Real behaviour is confirmed from public sources (PSPSDK headers, psdevwiki, uOFW) before fixing, and the knowledge base entry is updated as **confirmed** or **assumed**; what cannot be confirmed is recorded as assumed. No ad hoc correction that departs from the GE's behaviour (discarding a particular colour, nudging coordinates). Every fix comes with a probe, on synthetic data, that catches the defect again. Something unsupported must not pass silently: it shows in the statistics or in a warning printed once (the first unsupported texture format seen, an unsupported blend equation). No title name or address in code, probes or documents.

## 4. Verification for this task

1. Every fix has a probe, and it passes.
2. Win64 Debug/Release and Linux x64 Debug/Release builds and CTest; probes use no real game data.
