## Review 1 (2026-11-14, at `0e8ae98`)

Verification: in the consumer (reDMP1 #5) the real module ran from `module_start` to its first non-kernel call (`sceGe_user` `sceGeEdramGetAddr`) with no dispatch miss, unimplemented kernel NID or deadlock, and three runs gave the same HLE call record; the scheduler's baton structure, preemption and deadlock report, and the Vfs's path normalization and case-insensitive lookup follow the design. Fix the items in the table above. R2 (high): `SignalSema` and `SetEventFlag` wake every waiter and let each re-check, so whichever thread runs first takes the resource; the PSP (uITRON) semantics is a **handoff at signal/set time** in wait-queue order (FIFO or priority by the object's attribute) — decrement the sema count, or write the output bits and apply the clear options, for each waiter whose condition holds and make it ready — and today another thread running before the woken one can steal it, changing the order or deadlocking. Keep a wait queue per object (waiting thread, requested value, mode, output address) and hand off in queue order on signal, set, delete and cancel; attributes `0x100` (priority order) for semas and event flags and `0x200` (`WAITMULTIPLE`; without it a second waiter is an error) for event flags, values and meaning confirmed in uOFW and cited; a waiter's timeout includes removing it from the queue; the probe gains a steal reproduction (a higher-priority thread calling WaitSema right after the signal), FIFO and priority queue order, the `WAITMULTIPLE` refusal and the clear options. R3: the preempted thread goes to the back of its priority's ready queue, while uITRON/PSP keeps it at the front (**inferred**) — confirm in uOFW threadman and, if so, put preemption at the front and voluntary yields (waking from a wait, `RotateThreadReadyQueue`-like) at the back, citing the source in kb `scheduler.md`. R1: objects owned by the C++ frames that `RaiseStop` skips (`ExitThread`, forced termination, `ExitGame`, self-unload, stops) are never freed (`Invoke`'s `std::function` and `std::string` copies, a waiting handler's `shared_ptr`, ...); no lock is involved, so no deadlock, but every thread exit leaks — make `Invoke` hold no owning object while the handler runs (entries in stable storage called through a pointer, the call-count key built at registration), audit that no outer frame holds a lock on any path that may stop or wait and say so in comments and `ARCHITECTURE.md`, and document the bounds of the remaining leak (the handler frame of a thread force-terminated while waiting).

Order: R2, R3, R1. Afterwards rerun `redmp1 roms` three times in reDMP1 to recheck the stop point and determinism, and update reDMP1's `docs/analysis/boot.md` if the call order changed.

Done when: R1-R3 are in, the Win64 Debug/Release and Linux x64 builds and CTest pass, the reDMP1 boot is rechecked, and the work log has a "Review 1" section.
