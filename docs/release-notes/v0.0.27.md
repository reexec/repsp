# repsp v0.0.27

Texture filtering follows the game, with hardware sampling, mipmaps and anisotropy.

Issue [#59](https://github.com/reexec/repsp/issues/59):

- **Defects**: three were fixed.
  - The GE did not decode TFLT (`0xC6`).
  - The "Original" option was always nearest.
  - The GL shader read one texel with `texelFetch`, so no filter setting had any effect, the Linear and anisotropic options included.

  As a result, textures the game asks to magnify linearly (for example TFLT `0x000105`) showed their pixel blocks.
- **GE state**: TFLT, TMODE's maximum level, TBP/TBW/TSIZE for levels 1-7, and TEXLEVEL (mode and bias) are decoded.
- **GL**:
  - Reads go through `texture()` and sampler objects.
  - Original follows TFLT, Linear is always linear, and the anisotropic options use `GL_TEXTURE_MAX_ANISOTROPY`.
  - Game-supplied mip levels are uploaded. When the game supplies none, mipmaps are generated only for anisotropic filtering.
  - Render-to-texture is read bilinearly in the shader.
- **Software renderer**: bilinear when TFLT asks for linear (level 0 only).
- `ge_probe` and `gl_probe` check state, filters, levels, wrapping and render-to-texture.

Approximations:

- TEXLEVEL's slope mode is treated as automatic plus bias.
- Unused TFLT values (2, 3) fall back to bit 0.

Measured (one title, same input script, three runs):

- No unresolved-address dispatches.
- Present interval 18.9 ms, as before.
- 80 texture uploads.

Confirmed by the user in windowed mode.

Verified: build and CTest pass on Win64 (Visual Studio and Ninja) Debug/Release and Linux x64 Debug/Release.
