# repsp v0.0.30

Loading fixed-address `ET_EXEC` executables.

Issue [#65](https://github.com/reexec/repsp/issues/65):

- `module::ParsePrx`, `RelocateToBuffer` and `runtime::LoadPrx` accept `ET_EXEC` (`e_type 2`) as well as PRX (`e_type 0xFFA0`).
- Segments are placed at their link addresses without relocation; a caller base that differs from the lowest PT_LOAD address fails with an error naming both.
- An `ET_EXEC` with `SHT_PRXRELOC`, or with an entry outside its segments, is rejected.
- The module info is found at `.rodata.sceModuleInfo`'s address, or, without section headers, through the first PT_LOAD's `p_paddr` (a file offset).
- The PRX path and the API signatures are unchanged. `prx_probe` checks a synthetic `ET_EXEC`.
- Consumer: [reexec/reDMP2#1](https://github.com/reexec/reDMP2/issues/1).

Verified: build and CTest 23/23 on Win64 Debug/Release (zero warnings in repsp code); a consumer's real `ET_EXEC` executable loads and enters guest execution. Linux x64 in CI.
