# repsp v0.0.16

Crash capture, recovery from faults inside the scheduler's locked region, the audio wait's lost wakeup fixed, and probe timeouts.

Issue [#30](https://github.com/reexec/repsp/issues/30): a crash handler (native exceptions, `abort`, `std::terminate`, Linux fatal signals) writing a Windows minidump and a crash report (kind of termination, stop reason, guest thread and registers, recent HLE calls and guest entries, scheduler state, consumer extras); a run log file; input recording in the `--input-script` format; owner tracking for the scheduler mutex and **boundary recovery** (a thread that leaves guest code still holding the lock releases it, records "Stop/fault while holding scheduler lock" and ends the run; a self re-lock is handled the same way); stops are raised only after unlocking; the probe `crash_probe`. Commits `b60e2a6`…`30ee722` on task branch `i030-crash-capture`. Issue [#31](https://github.com/reexec/repsp/issues/31): the lost wakeup in blocking audio output fixed (a wake arriving after the audio lock was released but before the scheduler wait began was lost; `WaitCurrentIf` re-checks the condition under the scheduler lock); a 30-second CTest timeout for every probe. Same branch; squashed into this release's merge commit.

Decision (user): stops and faults inside the locked region are handled by "the rule plus recovery at the boundary". After recovery the state cannot be trusted, so the run does not continue: a crash report is written and the program ends (instead of a stop report).

Verified: Win64 Debug/Release (Ninja and Visual Studio) and Linux x64 Debug/Release builds with CTest 22/22; all six crash kinds leave a report on both platforms; 400 parallel `audio_probe` runs pass.
