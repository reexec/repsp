# repsp v0.0.4

GE and display: the display-list interpreter, a software renderer and interrupts.

Issue [#7](https://github.com/reexec/repsp/issues/7): `repsp_gpu` with the GE command interpreter (list queue, stall, the `CALL` stack, `SIGNAL`/`FINISH`), the backend contract and a software rasterizer drawing straight into guest VRAM (carried from psprecomp's MIT code with attribution); `repsp_hle_ge` (9 sceGe_user functions) and `repsp_hle_display` (6 sceDisplay functions, a 59.94 Hz vblank, SDL3 window present, headless mode, `REPSP_FRAME_DUMP`); runtime interrupts (a queue, a dedicated stack, no waiting inside a handler); `get_fpr`/`set_fpr` in the recompiled-code contract; a NID name table computed by SHA-1 so unimplemented NIDs are reported by name; the probes `ge_probe` and `display_probe`. Commits `c0426e8`…`a603c18` on task branch `i007-ge-display`, squashed into this release's merge commit.

Known limits: lists run to completion as soon as they are queued, so signal handlers run after the list; points, lines, patches, culling, stencil, colour mask, fog, texture filtering and mipmaps, skinning and morphing are not implemented yet (`docs/kb/ge.md`).

Verified: Win64 Debug/Release and Linux x64 Debug/Release builds with CTest 11/11. In the consumer reDMP1 the real module ran its two GE setup lists and went on deterministically to the next unimplemented call.
