# repsp v0.0.12

An optional OpenGL render backend.

Issue [#24](https://github.com/reexec/repsp/issues/24): platform — a GL 3.3 core context on the UI thread (also on a hidden window), a render job queue, GL function addresses, presentation of a GL texture; `repsp_gpu` — texture decoding shared by both backends and the `opengl` backend (command buffers executed on the UI thread; one render target per guest frame buffer at an internal scale of 1 to 8; fragment processing in the software backend's order; a texture cache keyed by content hashes; state batching; statistics); display — targets drawn by the GE are presented through GL, CPU-written frame buffers are uploaded from memory, and frame dumps are read back at scale 1; the probe `gl_probe` (pixel comparison of the two backends, skipped without a context). Commits `2f8d571`…`438cd2b` on task branch `i024-opengl-backend`, squashed into this release's merge commit.

The software backend stays the default and the reference. `repsp_gpu` does not depend on SDL, and there is no new external dependency.

Known limits: render targets hold 8-bit colour, so for 16-bit frame buffer formats the result differs from the software backend's (and the real device's) 5-bit quantization by up to 8 per channel. Guest CPU writes into a GE target area, and CPU reads of a frame buffer drawn by the GE, are not supported (a diagnostic option counts them). Blend combinations that GL cannot express are approximated and counted.

Verified: Win64 Debug/Release and Linux x64 Debug/Release builds with CTest 21/21. In the consumer reDMP1 the screens from the title to gameplay came out the same through OpenGL, with zero unsupported or approximated cases.
